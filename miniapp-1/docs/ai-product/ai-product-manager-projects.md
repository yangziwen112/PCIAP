**角色：全栈独立开发 / AI 产品设计与落地**

## 项目二：基于 AI Agent 与本地 OCR 的智能股票投研与持仓管理平台

**角色：核心链路开发 / AI 产品与数据链路设计**  
**开源仓库：** [yangziwen112-jushi-fund-research-open](https://github.com/yangziwen112/yangziwen112-jushi-fund-research-open)

- 主导“截图导入—OCR 识别—基金匹配—净值分析—风险提示”核心流程设计，落地本地 OCR 处理支付宝/微信持仓截图，并通过用户确认机制避免识别结果未经核验直接进入研究链路。
- 负责基金数据链路搭建，基于 FastAPI 实现后端服务，将历史净值分页增量写入 SQLite，区分盘中估值与正式净值链路，通过主源、备用源、缓存和 `insufficient` 状态保障数据语义真实，不用合成结果填空。
- 主导策略验证与风险提示模块建设，基于真实基金净值完成 400 个交易日样本外回测，优化 MA20 规则；同时保留训练/测试边界、基准、最大回撤和研究免责声明，避免将研究结果包装为投资建议。

## 项目三：Codex × OpenClaw × 飞书的多智能体协作交付工作流

**角色：AI 产品经理 / 多智能体协作流程设计与落地**  
**项目属性：日常协作实践，无独立 GitHub 仓库**

- 针对本地编码智能体缺少飞书数据操作、网页检索和团队协作上下文的问题，设计 Codex/VSCode 与飞书 OpenClaw 的角色分工：Codex 负责代码、文件、测试、Git 和本地证据；OpenClaw 负责飞书文档、多维表格、消息、日历、网页搜索和知识检索。
- 将自然语言协作变成可追踪任务协议：每次任务明确 `task_id`、目标、范围、禁止事项、预期产物、证据要求、风险边界和验收方式；OpenClaw 返回原始结论后，由 Codex 进行本地代码、测试、权限和数据状态核验。
- 落地异步桥接交互：通过本地 PowerShell bridge 提交任务并轮询结果，固定会话上下文；协作结果统一区分 `verified`、`partial`、`insufficient`、`needs-confirmation` 和 `failed`，避免把助手的自然语言建议误报为已完成事实。
- 建立“派工—执行—回传—核验—沉淀”的闭环：已形成飞书交付文档、协作日志、任务台账设计和本地交接材料；当飞书 OAuth 或多维表格权限不足时明确记录阻塞原因，不绕过权限，也不伪造写入结果。
- 将协作经验沉淀为可复用的任务模板、验收清单、风险边界和证据回传格式，能够把多智能体协作从聊天演示转化为面向真实项目的交付流程。

### 第三个项目的可落地交互契约

```json
{
  "task_id": "multi-agent-delivery-20260928-001",
  "objective": "核对两个 Git 项目的测试状态并生成可追溯的进度摘要",
  "scope_in": ["PCIAP", "fund-research-open", "飞书交付文档"],
  "scope_out": ["不修改外部数据", "不绕过 OAuth", "不提交私有配置"],
  "expected_outputs": ["测试结果", "提交哈希", "远程 push 状态", "阻塞项"],
  "evidence_required": ["命令输出", "时间戳", "来源或文件路径", "置信度"],
  "verification_method": "Codex 本地复跑测试并核对 Git 远程分支",
  "status": "verified | partial | insufficient | needs-confirmation | failed"
}
```

这个项目的核心能力不是让多个模型同时回答，而是把业务目标拆成角色、权限、工具、状态、验收和证据，使每个智能体都能在边界内完成可复核的工作。
